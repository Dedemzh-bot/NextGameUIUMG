# Explicit protected Designer-mode continuation

## Scope and distinct evidence

`designer-mode-continuation/1` is an explicit opt-in for an original new-build plan 0.2 that already declares the protected CDO fallback and failed exactly at `list-design-size-mode-property`, after its final official compile and CDO acquisition. It does not resume Create or rewrite the original plan/checkpoint. Duplicate failed observations of that same next step remain present and byte-bound. Other failures and partial official writes are rejected.

The single-purpose runner `scripts/designer_mode_continuation.py` produces a separate `nextgame-ui-designer-mode-continuation` receipt/1 under the closed `assets/designer-mode-continuation.schema.json`. It never presents NxUE operations as official MCP, never marks the old checkpoint completed and never replaces the subsequent actual-state or visual/result gates.

## Preflight and execution boundary

The runner binds the original failed plan/checkpoint, accepted Requirement/View/Bundle, exact canonical source-layout lowering, reviewed saved-asset SHA and explicit observed before enum. Continuation/1 is restricted to structured-source Requirement 0.2. The unique Bundle asset must bind this exact layout path/hash and the accepted Requirement/View's exact target Designer decision; a successful unrelated Bundle cannot authorize another plan. It calls the existing formal validators with those exact source arguments, independently obtains GetWidgets recovery evidence and requires an explicit clean official dirty result. The original complete creation prefix is validated in order; saved-result references are reconstructed from earlier event results, including hash-bound actual result sidecars. The final `checkpoint.saved` map cannot alter history.

An explicit loopback MCP URL is required. The existing NxUE CLI status must identify the same project and live server port. Local TCP listener ownership for that port and the MCP URL's port must identify the same Editor process. This is repeated before compile, the exact Designer setter, save and after completion. NxUE status has no assumed PID field. Different processes, proxy ambiguity or unknown identity blocks execution; no machine port or credentials are embedded in the package.

After fresh official compile, the runner reuses the existing-layout-v2 protected Designer preflight: actual generated CDO identity, official schema omission, live NxUE metadata supporting list/get/set with set-only writes, exact EnumProperty/CDO/class/package identity and before-value CAS. An exposed official field causes this fallback route to stop before writing. The sole NxUE write is `manage-property` setting that exact CDO's `DesignSizeMode` to the originally accepted `FillScreen` or `Desired`; immediate getter verification follows.

Immediately before compile, the protected setter and save, the physical saved-file SHA must still equal the explicitly reviewed original SHA, and all immutable formal inputs are rechecked. These CAS observations have their own filesystem provider. After save, immutable output bytes are captured immediately and must remain equal to the physical asset through final verification. Same-process identity alone never substitutes for this protection against another Editor's external save.

Official save, post-save reacquisition and exact Designer getter, the original remaining read-only tree/property observations, clean-state and same-process checks must complete. Before/after ordered actual WidgetTree identities must agree. The runner does not execute arbitrary Python writes, native setters, deletion, reparenting, event binding or general property changes. It does not automatically recover or roll back a failed continuation.

## CLI and Art consumption

`inspect --plan PLAN --failed-checkpoint CHECKPOINT` performs only offline original-prefix validation. `validate RECEIPT --plan PLAN` validates completed continuation evidence without Editor calls. `execute` additionally requires explicit `--capability designer-mode-continuation/1`, formal source paths, `--project`, `--url`, a new `--output` directory in project Saved, `--asset-sha256` and `--before-mode`. Use current CLI help for the complete arguments. Inspection is not execution authorization.

Art requests must explicitly include `designer-mode-continuation/1` alongside their existing `development-baseline/1` or `/2` capability. Their `buildEvidence` continues binding the original plan and exact artifact via its existing `checkpoint` file binding; only this opt-in permits that artifact to be the distinct continuation receipt. Ordinary checkpoint v2 completion, full ordered coverage and exact official compile/save requirements stay intact. The normal route now resolves `${...}` against preceding actual event results before comparing compile/save targets, correcting rejection of canonical variable-based plans.

The existing `art_pipeline.py init` compact job accepts the exact optional field `designerModeContinuation: "designer-mode-continuation/1"` only for `goal=formal-art` with an explicit developmentBaseline version 1 or 2. The initializer then adds that capability; omission never opts in. Its normal bound request/source validation remains required.

Execution consumes and permanently binds an immutable pre-execution Bundle. A later frozen development Bundle may advance only execution status/first recorded start, planned-to-built asset status and existing verification status/artifact evidence; Requirement, layouts, mappings, IDs, check types/references/claims and all other obligations remain exact. Only relative spellings of those same bound Requirement/Layout files may differ. The reader rejects removed/added obligations, erased failures, changed design content and compile/save artifacts pointing elsewhere. Thus a later real result does not need to overwrite its pre-execution source or predeclare success.

The continuation validates its real formal-source, process, typed property, compile/save and readback evidence; it is not a synthetic completed v2 checkpoint. A final baseline still requires complete source validation, normalized actual readback, current snapshot identity, Designer mode and separate visual/result acceptance. Tool-source publication and any new runtime execution require their own applicable authorization.
