# Requirement-driven build handoff

Use this contract when the task starts from an accepted `UIRequirementSpec 0.1` (raw analysis) or `0.2` (structured design) instead of a legacy standalone `UILayoutSpec 0.2`. Both sources share the same build and verification contract. For 0.2, first use `$receive-nextgame-design`; the real design source and exact compilation replace only the nine-role source proof, never semantic validation or result evidence.

## Review gate

- Validate the requirement and its source packet with `python ../analyze-nextgame-ui-requirements/scripts/validate_requirement_spec.py <ui-requirement.json> --request-packet <request-packet.json> --check-findings-files` when run from this skill directory. For 0.1, strict mode must load and validate all nine linked AgentFindings and their six context-aware inputs, verify file/context hashes and role pairing, and prove every findings local ID is either aliased or explicitly discarded. For 0.2, strict validation must bind the actual structured design contract and reproduce its adopted content exactly. A missing source, changed locked value or unresolved blocking design gap stops both planning and execution.
- Require `reviewGate.required: true` and `reviewGate.status: accepted` before creating build artifacts or connecting to Unreal Editor.
- Require the bundle link to match the accepted spec's `requestId`, `revision`, and `reviewGate.approvedContentSha256`; also hash the requirement file into `requirement.sha256`.
- Treat only claims whose status is `accepted` and which are listed in `reviewGate.acceptedClaimIds` as build-authoritative. Keep proposed, rejected, and unresolved content out of every generated `UILayoutSpec` and operation.
- Stop if the target contains a null field, no target path, no in-scope asset plan, or an open/unresolved item that is high-impact or has `blocksBuild: true`. Those shapes are valid only while review is pending.
- If raw references or a pending requirement are supplied, run the analysis skill and return its review summary. Do not continue into Editor mutation in the same turn.

## Accepted Build View gate

- After the complete Requirement passes the review gate, generate `Saved/CodexUIRequirements/<request-id>/accepted-build-view.json` with `python ../analyze-nextgame-ui-requirements/scripts/accepted_build_view.py <ui-requirement.json> <accepted-build-view.json>` and validate it with `python ../analyze-nextgame-ui-requirements/scripts/validate_accepted_build_view.py <accepted-build-view.json> --requirement <ui-requirement.json>`.
- [Accepted Build View 0.1](../../analyze-nextgame-ui-requirements/assets/accepted-build-view.schema.json) is non-authoritative execution input for the sole build-planning Agent. It parses and hashes one immutable snapshot of the complete Requirement bytes, then binds the physical file SHA-256, canonical SHA-256, request ID, revision, accepted approval digest, and Requirement Schema identity/digest. The full validator and View rebuild use the same immutable Requirement Schema bytes snapshot. The validator deterministically rebuilds the View from the external complete Requirement snapshot; an internally self-consistent but forged, stale, or cross-file-bound View is invalid.
- The View retains the complete accepted `request` and ordered `reviewResolutions` as exact copies. This prevents request exclusions, completion criteria, or a resolved pre-mutation gate from disappearing merely because its linked accepted claim is less specific. Its coverage ledger deterministically partitions all accepted claims, all elements, all nested states, and all acceptance criteria into projected IDs or explicit non-build records. Accepted claims are always projected. An element, state, or acceptance criterion may be non-build only when the complete Requirement declares `inBuildScope: false` with a nonempty `scopedOutReason` copied into the ledger. Other in-scope assets, regions, collections, runtime fields, and responsive intents are projection roots because the planner still needs their executable semantics. All accepted assumptions and answered questions are roots as well, so directional `affectsClaimIds` links cannot hide a reviewed build decision; proposed/unresolved assumptions and open questions stay outside execution input.
- Projection is a fixed-point transitive dependency closure over canonical IDs, not field deletion. Retained records preserve complete values and source order; every referenced canonical object is retained. State, axis, control-input, and state-model IDs share the whole state-model record as their physical owner, but only in-scope state IDs enter the executable side of the ledger.
- The complete Requirement must first pass its closed Schema, approval, canonical-reference, and semantic validators; an invalid Requirement is rejected before a View can authorize anything. For a valid authority, an unaudited Schema version or open-payload reference shape, missing scope classification, incomplete closure, projected owner/value mismatch, or incomplete coverage produces an exact `mode: full-fallback` copy of the complete Requirement with `buildAllowed: false`. Stop before planning or Editor connection. Never continue automatically merely because the fallback content is complete.
- Give the planning Agent only a validated `mode: projected`, `buildAllowed: true` View. Keep the complete Requirement as a validator-side authority and preserve it as `bundle.requirement.path`; the View never becomes a Bundle Requirement link and never changes the final `UIRequirementSpec` format.

## Build-planning ownership

- Use one build-planning Agent as the sole writer of the authoritative `UIBuildBundle` and generated layout specs. It consumes the validated Accepted Build View, not another full Requirement copy, and must not modify the View or its coverage classifications.
- For Bundle 0.1, emit one `UILayoutSpec 0.2` per asset in accepted `assetPlan` scope. For Bundles 0.2, 0.3, and 0.4, an asset with `representationKind: layout-spec` receives a layout; a `reuse-only` shared extension or empty-tree Parent Class child is represented by `reuseRelations` and must not receive a fake layout root. When that empty-tree child is nested through `widget-tree-instance`, use `childSizingCompatibility.mode: inherited-reuse-only-full-stretch` only for a full host rectangle. Under HorizontalBox/VerticalBox use `inherited-reuse-only-flow-slot` with exact `content-driven` or `weighted-remaining-space` allocation; under GameScrollBox use `inherited-reuse-only-scroll-slot` with `scroll-slot` sizing and no Box Size. Every inherited mode names the exact Parent Class and prototype-extension relation IDs; never fabricate `sourceLayoutNodeIds`. Use 0.3 for new dual-layer shared reuse, or 0.4 when art is requested; 0.2 is closed historical compatibility only.
- Preserve the dependency order `entry -> child widget -> screen` and record cross-asset collection or child-widget integration in the bundle.
- Use only the selected version's closed top-level fields. Bundle 0.1 uses `version`, `bundleId`, `requirement`, `assets`, `nodeMappings`, `crossAssetOperations`, `execution`, and `verification`; Bundles 0.2, 0.3, and 0.4 additionally require `reuseRelations`; 0.4 also requires `artStage`. Bundle 0.2 keeps its single `namedSlot`/`inheritedSlot` shapes; Bundle 0.3 uses dual `namedSlots`/`inheritedSlots` shapes and must not accept the old fields. Put deviations in `verification.deviations`, not at the top level.
- In Bundle 0.3 or 0.4, the shared extension records `SlotDown` first/strictly-lowest and `SlotUp` last/strictly-highest as Auto Size disabled, full-fill, `IsVariable`, `SelfHitTestInvisible` root-direct children. A direct-add relation may have no legacy names; a migration relation preserves the concrete legacy NamedSlots and bindings found by readback (`Slot1` is specific to the current bag-item asset). Every Parent Class relation records both inherited Slots in `SlotDown`, `SlotUp` order. Each is `empty|panel`; both may be `panel`, but each used Slot has exactly one direct semantic Panel and defaults to full fill.
- For a brand-new project-common `layout-spec` asset only, Bundle 0.3 or 0.4 may replace the extension relation's ordinary `registry` field with a content-addressed Bundle-local `bootstrapSnapshot`. The snapshot is non-executable plan evidence and contains only `expected*` identity, layout/contract digests, accepted authorization, and the exact base Registry digest/revision; it never contains fabricated Unreal readback or actual interface/reuse hashes. Keep every transitive consumer `planned` until the prototype is compiled, saved, freshly read back, atomically published as active, and the Bundle is rewritten with a real `registry` binding plus verified activation. The same premature-consumer gate applies to an existing Registry candidate awaiting activation. During either pending phase, an unverified WidgetTree generation/parameter contract may be referenced only by an empty `parameterOverrides` planning relation; any override, advanced consumer, or finalized lifecycle requires the active verified Registry contract. Rerun both strict validators between phases. Existing assets and `reuse-only` sources cannot use bootstrap.
- Give every UILayoutSpec node exactly one `nodeMappings` record. Store canonical requirement IDs in `requirementRefs`, accepted claims in `claimIds`, and state IDs in `stateRefs`; use `mappingKind: generated-support` for helpers while still linking a real accepted requirement and claim.
- Cover every accepted in-scope asset, region, element, collection, runtime field, responsive intent, and state through assets/mappings, and every accepted in-scope acceptance criterion through `verification.checks`.
- Preserve element semantics while lowering: one canonical `image` maps to exactly one realization—normally one `visual.image`, or one `widget-tree-instance` relation when a verified shared control supplies the complete graphic. `text` maps to `text.*`, `button` to `input.button`, progress to `progress.*`, and structural Panels to compatible `container.*` roles. Every new `visual.image` maps back to exactly one accepted image element; a region, Panel, or `generated-support` mapping cannot authorize extra point/line fragments, and local images cannot duplicate relation-backed visuals. An accepted additional image layer remains a separate canonical image with its evidence-backed split reason.
- Treat every accepted complete static image or independent image layer as a real node even when no matching art resource exists. Use a non-variable `visual.image` / project `GameImage` with an explicitly recorded temporary whole-graphic brush or placeholder; lack of art never authorizes omission, but it also never authorizes rebuilding one recognized graphic from many primitive images.
- For every screen region or screen-level element with accepted geometry, copy its accepted normalized bounds unchanged into the matching screen UILayoutSpec node. The child asset's `referenceSize` is local implementation metadata and may not be used to derive the screen node's host bounds.
- Apply the formal target-basename guard before lowering the accepted per-asset interface-analysis decision. Every `umg_*` target requires `profile.designSizeMode: FillScreen`; reject a Requirement decision that tries to assign `Desired`. For `uw_*`, copy the accepted analyzed `Desired|FillScreen` decision exactly; a missing/unclear decision resolves to `fallback-unclear -> FillScreen`. Unknown/legacy basenames resolve to `fallback-unknown-target -> FillScreen`. Do not derive the result from `assetPlan[].assetKind` or directory, and do not duplicate it as an independently editable Bundle field. `Desired` requires an executable UILayoutSpec proof: at least one root-direct child has a point-anchored Canvas Slot with `autoSize: false` plus positive width/height offsets, or declares `verified: true` content-driven size with positive `measuredDesiredSize` and an accepted `evidenceId`. Empty, auto-sized fixed, verified-only, and zero-offset full-stretch-only roots are invalid. The list-entry first-Panel contract remains stricter. A reuse-only child has no fake Layout, so execute and verify its guarded Requirement/Bundle decision directly rather than guessing from a missing layout.
- When a child asset is placed in a screen host whose bounds differ from its local `referenceSize`, record an explicit host strategy in the build operation: Fill/stretch for a shared rectangle, flow sizing for content-driven layout, or ScaleBox only when deliberate scaling is part of the accepted design. Placeholder `ReplaceWidgetWithTemplate` operations are not formal child integration and cannot satisfy the mapping or verification contract.
- Set `profile.explicitPanelSlots: true` on every new layout. When the accepted Requirement enables `explicitPanelSlotsRequired`, copy each direct child's `panelSlotIntent` exactly into `flowSlot` or `scrollSlot`, and prove that its parent mapping uses the declared `layoutRole`; never leave Size, Padding, or Alignment as prose or infer them from `rect`. A relation-backed child carries the same decision in `widget-tree-instance.placementContract.slot`: `HorizontalBox`/`VerticalBox` includes Box Size, while `GameScrollBox` does not. For content-driven Box children, use Size `Auto` and `sizingStrategy: content-driven` even when an Alignment is `Fill`; for weighted Box children, use Size `Fill` with a positive weight and `sizingStrategy: weighted-remaining-space`. A reuse-only Parent Class child uses `inherited-reuse-only-flow-slot` with the matching flow allocation, or `inherited-reuse-only-scroll-slot` plus `scroll-slot` for a GameScrollBox child, rather than pretending either case is `fill-host`.
- Map each image element-targeted responsive intent on the same realization as its target image and copy its horizontal/vertical decision into direct-node `adaptiveLayout` or the relation-backed nested-instance Slot. When `explicitImageOwnerIntentRequired` is enabled, also map each inherited image's exact `ownerIntentId` once to the declared region/ancestor owner node or nested-control relation, require its two-axis adaptation to match, and prove the image realization is structurally inside that owner through node ancestry or an explicit child/reuse integration chain. Every relation used for this proof records exact `parentWidgetName` and content-derived `parentTreePath`, including Canvas/Overlay placement. The layout validator checks Canvas, Overlay, flow, and scroll child Slot alignment. `adaptiveLayout` controls occupancy inside the allocated Slot; it never replaces the authoritative Box `flowSlot.size` decision.
- Validate every generated layout with the existing layout validator, then run both `python ../analyze-nextgame-ui-requirements/scripts/validate_build_bundle.py <ui-build-bundle.json> --accepted-build-view <accepted-build-view.json>` and `python ../analyze-nextgame-ui-requirements/scripts/validate_requirement_coverage.py <ui-build-bundle.json> --accepted-build-view <accepted-build-view.json>` before connecting to the Editor. Both validators still read and fully validate the complete Requirement recorded by the Bundle; the View is only an additional deterministic gate. Use `--requirement <ui-requirement.json>` only when overriding that full path, never to supply the View, and do not use `--skip-linked-files` for this final gate.

## State lowering

- For `exclusive-panel-branches`, materialize every accepted state branch in one WidgetTree. Keep each branch's own GameImage, TextBlock, font, geometry, decoration, and adaptive layout.
- Make every program-controlled state-branch Panel a variable. Use `SelfHitTestInvisible` for the initial active passive branch and `Collapsed` for inactive passive branches. Use `Hidden` only when layout space must remain reserved and the requirement branch has `preserveLayoutReason`.
- For every accepted state model whose `controlInputs[].kind` is `user-interaction`, make the assigned asset interactive and add a hit-area `input.button` named `Btn*` that owns the click/tap trigger surface. Put the complete state presentation under its direct content layout or another validated layered structure. A state mapping backed only by Panels, GameImages, or TextBlocks is incomplete; project code still owns the actual transition.
- Let a Button directly own its CanvasPanel content host. Do not introduce a one-child Overlay between the Button and CanvasPanel. The direct CanvasPanel must explicitly declare its UILayoutSpec `buttonSlot`: use zero padding and Fill on both axes for whole-button coverage, or preserve accepted finite Padding for an intentional content inset. Explicit supported Slots on other direct Button children are lowered too; the current schema supports Fill/Fill only.
- Use `shared-tree-properties` only when accepted states share the same topology and differ by a small set of properties that project code will control.
- Do not synthesize Cartesian combinations of independent state axes unless an accepted requirement explicitly defines that combined presentation.

## Child-instance state handling

Without the versioned `shared-node-states/1` extension below, a `stateAssignment` realized entirely inside its owning screen does not require a cross-asset operation only when exactly one same-screen `nodeMappings` record proves the route. That mapping must belong to a Bundle `screen` asset whose matching Requirement `assetPlan` covers both the assigned element and every state model named by the assigned states; use `mappingKind: direct|composite-state`; make `stateRefs` exactly equal the assignment; and include exactly one assigned target element in `requirementRefs`, namely that assignment's element. An absent, incomplete, non-screen, or ambiguous same-screen route does not relax child-instance handling.

Without the versioned `shared-node-states/1` extension below, every true child or entry instance mapping with `stateRefs` requires one cross-asset operation whose `stateHandling.stateRefs` exactly match the mapping and its requirement `stateAssignment`. The reverse also holds: every state-handled operation must target a mapping that names exactly one requirement element with one unique assignment, and all three state-ref sets must match. Select exactly one schema strategy:

- `owning-screen-state-tree`: use `child-widget-integration` into a screen and map every complete state composition as branch nodes in that screen; do not also map those state nodes into the source child.
- `static-variant-asset`: use `child-widget-integration` from a child-widget asset whose plan covers the state model and whose mappings contain exactly the assigned state refs and complete composition.
- `instance-parameter`: use `instance-state-initialization` and provide `parameterName`.
- `runtime-dependent`: provide `previewExclusionReason` and an accepted structured deviation through `deviationId`. The exclusion applies only to the runtime-dependent preview, not to requirement mapping or coverage.

## Versioned singleton state and content-size capabilities

Bundle versions 0.1–0.4 may opt into the closed, unique `capabilities` values below. An omitted capability preserves all historical exact-match checks. New fields or strategies without their capability are errors, not legacy fallbacks. Requirement schemas and their projection/reference authority remain unchanged.

### shared-node-states/1

For an accepted `shared-tree-properties` model, a singleton node can support multiple states without authored duplicates. Its mapping uses `stateRefs` for supported states and `initialStateRefs` for the exact per-instance `stateAssignment`. Initial states must belong to the supported set and must match the accepted exclusive-axis assignment. Supported states must map every required composition element exactly once in the proper owning asset; listing state IDs on unrelated nodes does not establish coverage. Historical exclusive branch and static variant behavior remains unchanged.

Initial-axis coverage is checked against models that directly assign the mapped element. Membership in another model's parent composition does not create a second direct assignment on every descendant; that model's assigned parent must retain its own complete initial state. Singleton host overrides accept the canonical `Visibility` spelling and the existing `visibility` spelling, and lower both to the actual `Visibility` property; this is a specific compatibility alias, not case-insensitive or arbitrary property access.

A real child instance whose properties are controlled by its screen uses `stateHandling.strategy: owning-screen-shared-properties`. Its supported and initial refs must match the target mapping, and `propertyBindings` contains exact `{stateRef, elementId, property: "Visibility", value}` records derived from the accepted overrides. The target must be the correct variable child instance, its initial Visibility must match the initial state, and the source child must not claim screen-owned state composition. This creates no runtime event interface or business behavior.

### content-driven-child-size/1

This capability permits the validated `layout-dependency/1` plan-size proof and the `fixed-width-content-height` child sizing compatibility form. The latter binds `axes`, `sourceLayoutNodeIds` and positive `fixedWidth` to the source child: the width matches the accepted local reference width, the source has a validated content-size proof, and the screen host uses point anchors plus `autoSize` so height can grow. It does not require vertical stretch and does not use the source reference rectangle as the screen placement rectangle.

The `/1` contract conservatively permits one visible direct content subtree under the source Canvas root, cited exactly once. Its anchors, left/top offsets and alignment are all at the local origin; other visible siblings or shifted content are rejected because they can enlarge the complete widget's Desired Size. Inspect all visible image sizes, text wrap widths and supported Slot padding when proving the width upper bound; citing only a minimum-size source is insufficient.

These opt-ins cannot replace compile/save, actual WidgetTree/property readback, live width/height and long-text checks, state previews, rerun idempotence or post-build user acceptance. Migrate a current task explicitly, keep its old Requirement/View/Bundle/evidence snapshots intact, and regenerate all affected bindings.

### content-driven-child-size/2

This is a distinct explicit capability; do not declare `/1` and `/2` together. It uses the existing closed `fixed-width-content-height` compatibility fields without inventing a new placement operation. Cited root-direct `contentSizeProof` records must use the closed `layout-dependency/2` kind. The real source root content is a single origin-aligned width-only SizeBox, with `fixedWidth == sizeBoxConstraints.widthOverride == minimumDesiredSize[0]` exactly. The integer local design reference width is exactly `ceil(fixedWidth)`; it is not the actual width or an allowed width tolerance. The screen host retains point anchors, content-driven sizing and Canvas Auto Size.

The version 2 proof validates the complete supported subtree, propagating known available width only through actual SizeBox constraints and explicit horizontal Fill alignment. It reserves Auto sibling bounds and padding before allocating positive HBox Fill weights to text leaves. Graphic sources remain non-Fill; vertical Fill, unknown width authority, hidden/unreachable sources, negative values, cycles and fixed-height substitutions are rejected. Natural height still comes from the positive lower bound of reachable visible graphic sources, not a fabricated font or Slate measurement. A finite complete-subtree width upper bound is mandatory. See [the exact layout contract](layout-spec.md#fixed-width-natural-height-dependency-v2).

Accepted fixed wrapped Canvas text separately uses the closed `textCapacity` kind `bounded-wrap/1` from [Bounded wrap capacity v1](layout-spec.md#bounded-wrap-capacity-v1). It keeps `autoSize: false`, exact positive capacity dimensions and stable placement. It does not grant a runtime max-lines property or promise actual text fit. Preserve the accepted evidence and inspect representative longer strings after execution. Neither opt-in changes locked design geometry, preserves an old approval after migration, or replaces post-save property/geometry/visual evidence.

## Trial coordinate handoff

For explicit `source-target-coordinates/1`, validate the Requirement `coordinateContract` before lowering. Preserve original image observations and the bound pre-coordinate source snapshot. Put exact accepted target rects and Slot projections into Layout nodes and bind each Layout with `{capability, version: 1, contractSha256, assetId, requirement: {path, sha256}}`; Bundle binds `{capability, version: 1, contractSha256}`. `contractSha256` uses UTF-8 canonical JSON with sorted keys, compact separators and unescaped Unicode. `assetId` is the Requirement asset-plan identity; Bundle asset IDs may differ through their existing `assetPlanId` relation.

A `coordinate-design-derivation` version 1 file has exactly `kind`, `version`, `requestId`, `boundary: "design-derived-not-source-transform-proof"`, `script: {path, sha256}`, nonempty `inputs: [{path, sha256}]`, and `records`. Each record is the target's exact six-field projection: `assetId`, `layoutNodeKey`, `subjectRefs`, `coordinateSpace`, `rectPixels`, `slotContract`. Paths resolve against their containing file. An independent `coordinate-design-review` version 1 file has exactly `kind`, `version`, `requestId`, `status: "passed"`, actual `reviewer`, timezone-aware `reviewedAt`, `derivationSha256`, and `records: [{assetId, layoutNodeKey, recordSha256}]`. Record hashes use the same canonical JSON algorithm. Do not label draft review or expected geometry as actual review, capture or pass evidence.

`source-transform` and `design-derived` each require existing evidence and accepted reviewed claims. Only the former claims exact source-transform equality. A saved full-frame registration may supply a newer source observation through `{path, sha256, recordKey}` without modifying older raw bounds. The ordinary prepare, Coverage and Bundle preview validators consume the opt-in; there is no extra preliminary CLI. See [trial coordinate rules](project-layout-rules.md#trial-source-and-target-coordinates). This trial capability does not promote a screen-specific layout correction into a global design recipe.
